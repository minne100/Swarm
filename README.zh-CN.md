# Swarm Paradigm（蜂群范式）

[English](./README.md) | 简体中文

将模糊的人类目标，转化为可执行、可测试、可审计、可交付的 AI 工作流系统。

## 项目定位

Swarm Paradigm 不是“让 AI 聊天更聪明”，而是“让 AI 像工程系统一样持续交付”。

它通过 Bee / Honey / Dance / Hive 的分层抽象，把复杂业务流程拆成可管理的最小单元，并在人类审核下完成端到端执行。

## 为什么叫“蜜蜂 / 蜂群”

这个命名不是营销包装，而是系统设计隐喻：

- **Bee（蜜蜂）**：单只蜜蜂专注完成一个微小动作，对应系统中的原子能力单元
- **Honey（蜂蜜）**：蜜蜂产出的标准化产物，对应可传递、可复用的数据契约
- **Dance（蜂舞）**：蜜蜂通过舞蹈传递方向和任务信号，对应流程编排与协作协议
- **Hive（蜂房）**：蜂群的组织与治理中心，对应执行环境与任务治理
- **Swarm（蜂群）**：整体协同而非单体智能，对应多 Agent 分工协作系统
- **Beekeeping（养蜂）**：养蜂人不替蜜蜂飞行，只做观察与校正，对应“人类只审核与纠偏，不直接写 Bee/Honey/Dance”

这套命名强调一个核心理念：**复杂目标不是由“一个超级 Agent”完成，而是由可组合、可治理、可审计的协同群体完成。**

## 设计原则（硬约束）

以下是项目核心边界，属于 MUST 级约束：

1. **Bee、Honey、Dance 必须由 AI 生成**  
人类不直接写这三类代码/定义，人类只负责审核、验收与纠偏（Beekeeping）。

2. **所有执行必须可追踪、可复盘、可审计**  
每个阶段都要有可解释中间产物和执行记录。

3. **复杂流程优先，轻量自动化次之**  
项目目标是处理复杂业务协作，不是替代简单脚本工具。

## 核心概念

### 1. Bee（原子执行单元）

Bee 是 AI 生成的 JS 类，只做一个原子功能。它的核心特点包括：

- 支持等待和挂起（可异步长流程运行）
- 工作完成或发生异常时都必须输出报告
- 本身不保存任何 Honey，数据完全由外部注入
- 处理完成后，结果与报告一并通过 Dance 提交
- 与外部能力解耦，接口化依赖注入
- 必须附带测试类，目标是覆盖全部测试用例（100%）
- 独立版本管理，可指定版本运行

一句话：**Bee 是可独立验证、可替换、可演进的最小生产单元。**

### 2. Honey（标准数据契约）

Honey 是 AI 生成的 JSON 数据包，是 Bee 间协作的数据载体：

- 类型必须明确
- 支持嵌套
- 不支持 `Object` 类型
- 用于跨步骤传递业务上下文与结果

### 3. Dance（流程编排定义）

Dance 是 AI 生成的 JSON 流程定义，用来描述“谁在何时做什么”：

- 定义执行顺序、并行与异步策略
- 定义超时、重试、异常与回滚策略
- 定义日志记录、提交规则与交付出口
- 每一步都应具备可供人类理解的描述

### 4. Hive（执行与治理环境）

- Bee 注册与调度
- Dance 执行引擎
- 任务审查与交付汇总

### 5. Swarm（上层协调系统）

Node.js 协调层，负责：

- 需求拆解
- 流程组装
- 模型与工具调度
- TUI（可扩展 Web）

### 6. BeeHub（能力市场）

- 共享可复用 Bee
- 检索现成能力
- 降低重复构建成本

## 记忆宫殿（Memory Palace）

这是 Swarm 的关键能力之一，用于长期上下文治理与 Token 成本控制。

核心作用：

- 从历史交互中筛选“与当前任务强相关”的记忆片段
- 降低无关记忆召回，提升召回精度
- 减少大模型上下文冗余，显著降低 Token 消耗
- 结合知识图谱形成可持续积累的组织记忆

产品意义：**越用越省、越用越准、越用越懂你的业务。**

## 典型工作流

1. 用户输入业务目标（自然语言）
2. 系统进行目标拆解与澄清
3. AI 生成 Bee / Honey / Dance
4. Hive 执行流程并产出中间结果
5. 人类进行 Beekeeping（审核与纠偏）
6. 输出最终交付，并沉淀图谱与记忆宫殿

## 关键特性

- 模块化：能力原子化、低耦合、高复用
- 可编排：流程可组合、可迭代
- 可测试：Bee 强制测试保障
- 可审计：结果有来源，过程可回放
- 可恢复：支持异常处理与回滚
- 分布式友好：支持跨线程/进程/主机
- 可视化：集成 graphify 形成关系图谱
- 记忆治理：记忆宫殿降低召回噪声与 Token 成本

## 产品经理视角：可行性与意义

### 一、为什么有意义

1. 把 AI 从“回答工具”升级为“交付系统”  
2. 解决复杂流程中多角色协作失控问题  
3. 沉淀可复用资产（Bee、Dance、知识图谱、记忆）

### 二、可行性分析

#### 1) 需求可行性

适用于：

- 复杂业务流程自动化
- 跨角色协同（产品/运营/研发/测试）
- 需要可审计和可追责的 AI 生产链路

#### 2) 技术可行性

成立基础：

- Node.js 编排生态成熟
- JSON 契约适合跨模块协作
- Agent 调度、状态机、队列体系已有成熟实现范式
- graphify + 记忆宫殿可支撑“可理解 + 可压缩上下文”

关键挑战：

- 任务拆解稳定性
- 长流程一致性与故障恢复
- 质量评估与自动化验收标准

结论：**技术可行，关键在于用 MVP 分阶段验证质量与成本。**

#### 3) 商业可行性

可探索路径：

- 开源核心 + 托管平台
- 企业版（审计、安全、权限、私有化）
- BeeHub 生态分成

### 三、建议的 MVP 范围

- Bee 规范 + 运行时
- Honey 契约校验
- Dance 基础编排（顺序/并行/超时/重试）
- Hive 日志与审计
- 记忆宫殿最小能力（任务级相关记忆提取）
- 一个可闭环业务模板（拆解 -> 执行 -> 测试 -> 报告）

### 四、建议关注的指标

- 端到端完成时间（TAT）
- 人工审核次数
- 首次交付通过率
- 异常恢复时间（MTTR）
- Bee 复用率
- 单任务 Token 成本下降比例

## 适用与不适用

适用：

- 需要处理复杂流程但团队人力有限
- 希望构建“可持续交付 AI 系统”的组织

不适用：

- 仅需一次性问答或轻量脚本自动化场景
